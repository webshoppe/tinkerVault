# Project Summary, Hermes Console

This is the story behind the tool, not the tool itself. If you just want to use it, `README.md` is right here in the same folder.

## Why this exists

Every existing Hermes frontend, including Open WebUI, talks to the API server-to-server. None of them can do the one thing this project actually needed: surface an approval-gated tool call and let a person resolve it from a phone or any second device. That gap wasn't theoretical. Earlier mobile-access testing hit it live: a delete fired without approval because the client had no way to even display the decision, let alone act on it. Checking the full list of frontends Hermes's own docs test against confirmed none of them speak the Runs API either. That's not a client bug anywhere, it's a missing feature category, and building a narrow tool for exactly that gap, not a general-purpose chat client, is the entire scope of this app.

## Build engine and constraint

Built entirely by `cn-fleet`, the isolated Hermes profile running `tencent/hy3:free` via OpenRouter, ahead of that model's free-access window closing (~2026-07-21). Same isolation design as everything else that profile touches: no git access, no credentials beyond its own scoped OpenRouter key, no shared history with the main profile. Whatever happened during the build, the blast radius was a working folder, nothing more.

## Build plan: five phases, ordered so the reason for existing lands first

**Phase 1, approval flow end to end.** This is the entire reason to build this instead of just using Open WebUI. One real unknown going in: the docs describe the approval endpoint's existence and purpose but don't enumerate the exact SSE event shape a run emits when it pauses waiting on a decision. Rather than let the build invent a plausible-looking event name, the plan called for probing a real approval-gated command against a live server first and building the parser against what actually came back, not a guess.

**What that probe actually found.** The target server's `GET /v1/runs/{run_id}/events` endpoint is missing its `Access-Control-Allow-Origin` header, every other endpoint sends CORS correctly, just not that one. A browser blocks the cross-origin read outright. Rather than ship a feature that silently fails in exactly the environment it's meant for (a browser, on a phone, talking cross-origin to a Tailscale host), the app polls `GET /v1/runs/{run_id}` every ~1.5s instead. The fetch-based SSE reader is retained in the code behind `const USE_SSE = false`, not deleted, so flipping one flag is all that's needed if the server-side CORS gap ever closes. The same reasoning applied to `/api/sessions/{id}/chat/stream`, a streaming endpoint avoided for the same cross-origin reason.

**Phase 2, connection and capability handling.** Host/port/key entry, stored per-device in `localStorage` (a real standalone browser app, not a Claude artifact, so this is the correct persistence choice here). `GET /health` and `GET /v1/capabilities` checked on connect, with the UI gated on advertised feature flags rather than assuming a given server build supports everything. This is the documented pattern the Hermes API docs describe for exactly this situation, so external UIs can detect support and fall back safely, not an invented workaround.

**Phase 3, session browser.** List, open, create, and fork sessions via the Sessions API, with defensive field-name access (`sessionId`, `sessionTitle`, `sessionUpdatedAt` helpers probing several plausible keys) since the exact response shape isn't contractually fixed by the docs. The first raw response from list/poll is logged and dropped into an on-screen debug panel specifically so real field names are easy to confirm against, rather than assumed once and forgotten.

**Phase 4, PWA shell and polish.** Manifest, service worker, install prompt, visual pass. Mid-build, an earlier working assumption from Phase 4 planning, that service worker registration was being blocked by the build agent's own sandbox, turned out to be incomplete. A real bug was hiding behind that assumption: `dom.installBtn` was referenced in the boot script before it was ever registered, which threw at load and aborted the rest of the boot sequence, including SW registration, and the resulting error was opaque enough in the sandbox to look like an environment limitation rather than a code bug. Found and fixed in Phase 5, verified clean in a real browser. Worth remembering: a plausible-sounding sandbox excuse is still worth re-checking once a fresh angle is available.

**Phase 5, release packaging.** Matching the precedent already set by Markdown Viewer v1.1.0: a `releases/` snapshot, `USER_GUIDE.md` and `DEV_GUIDE.md`, `VERSION` starting at 1.0.0, root README and CHANGELOG entries.

## What got independently verified, not just self-reported

Approval gating specifically was checked against live screenshots during the actual Phase 4 build, real Run/Reject/Command approval UI appearing mid-build for a Python/PIL dependency check and for an `rm -rf` cleanup step, confirming the gating mechanism works correctly in practice. That mattered because an earlier, unrelated finding (pre-dating this build) had suggested some tool calls went through ungated; this build's own evidence shows gating is command-dependent and working as intended, not uniformly broken.

## Self-improvement, observed twice during this build

The build agent's local `offline-html-tools` skill patched itself during this arc, twice. First, mid-Phase-3, it created an entirely new skill, `browser-api-client`, logging the change inline rather than silently. Second, during Phase 4, it patched that same new skill again, meaning it was iterating on something it had created for itself, not only refining the older skill. Both patches were read in full afterward and judged legitimate, no red flags, but `browser-api-client` specifically was kept local to the cn-fleet profile rather than promoted anywhere else, pending a fuller audit. Worth noting for anyone reading this cold: these review log entries surface several minutes after the actual work finishes, not inline with it, a quiet stretch during a build isn't the same as "nothing happened."

## One naming fix caught before shipping

`DEV_GUIDE.md` originally described the human publishing step as "a human (JP) through the GitHub web UI." Per this project's public-facing naming convention (`webshoppe`/`webShoppe` in anything repo-bound or generated for/by a build agent, "JP" reserved for private/internal notes), that line was corrected to "webShoppe" directly in the source before this release folder was cloned from it, so both the working copy and this shipped copy are clean.

## What shipped in v1.0.0

Connection screen, capability-gated UI, chat, remote approve/deny of tool calls, run stop, session browse/open/create/fork, and an installable PWA shell (manifest, service worker, custom install button, maskable and standard icons). Per-message toolbar (copy, rerun) was scoped and deliberately deferred to v1.1, recorded in this app's own `CHANGELOG.md` so it isn't forgotten. The footer's version field is currently blank on the live server, confirmed as graceful degradation working as designed (`renderPoweredBy()` skips fields it can't find), because the live `/v1/capabilities` response doesn't expose version in any shape the function checks yet, not a bug, just a low-priority v1.1 item.

## Human-in-the-loop publishing

All GitHub operations, commit, push, tag, release, are done by hand by webShoppe through the GitHub web UI. `cn-fleet` never touches git, by design, same as every other app in this repo. This build environment stages upload-ready file batches, grouped by target folder, each with a prepared commit message; nothing is pushed automatically.

## What's carried forward, not part of this app

A display-only bug in Hermes Agent's own dashboard (session titles falling back to raw `run_` ids instead of a message preview) surfaced during this same window. Confirmed by request/response shape (`GET /api/sessions`, port 9119) to live entirely in `NousResearch/hermes-agent`'s own upstream code, not in `hermes-console` and not in any fleet-built code. Deliberately not touched here, live shared infrastructure and someone else's codebase isn't something to hand to an unattended build agent. Logged separately, not yet fixed, two paths identified (a local patch that would get wiped on the next Hermes update, or an upstream PR), neither started.

## v1.1.0 (2026-07-18): a per-message toolbar, a real bug caught mid-build, and a scoping correction

Two scoped fast-follows on top of the shipped v1.0.0 app, both named in v1.0.0's own CHANGELOG as deferred rather than discovered late.

**Per-message toolbar.** Every rendered chat message gained a small action row: Copy (any message, via the Clipboard API with an `execCommand` fallback for non-secure contexts) and Rerun (user messages only, resubmits the exact input as a new run through the existing send/stream/poll path, no history replay). A real bug surfaced and was fixed during the build: the Send button's click handler passes a `PointerEvent` as its first argument, and an early implementation coerced that event object directly into message text (`String(text).trim()`), corrupting every message with `[object PointerEvent]` instead of the actual input. Fixed by guarding on `typeof text !== "string"` before using it. Verified live afterward: real message text flows through correctly, a new `run_id` is created on Rerun and threads into the session via the existing polling logic, and the toolbar shows Copy-only on assistant messages versus Copy+Rerun on user messages. Clipboard *write* was confirmed firing with the exact string; clipboard *readback* (an actual OS paste) is flagged as unverifiable by a sandboxed harness, the same documented ceiling this project has hit before with `offline-html-tools`, worth a human smoke test rather than treating it as fully verified.

**A scoping correction, mid-arc.** The first build pass investigated the footer's `powered-by` line (the connected server's own agent/version info), confirming no version-like field exists anywhere in the live `/v1/capabilities` response and leaving the function untouched, a legitimate, complete finding, but not actually what was being asked for. The real, still-open gap was that Hermes Console never displayed its *own* version anywhere in its UI, not the connected server's. A follow-up pass added a small version label next to the header title, reading it from `./VERSION` at runtime (rather than hardcoding it, so the displayed number can't drift from `CHANGELOG.md`/`README.md` the way this project's docs have drifted before) with a static placeholder fallback for contexts where `fetch()` can't run (`file://`). Verified live on both the connection screen and the connected chat view, confirmed not to duplicate or interfere with the unrelated `powered-by` line.

**A structural gap this pass surfaced, worth naming plainly.** The docs/build-process/releases restructuring applied to v1.0.0 before it shipped only ever touched a downstream review copy, not the app's actual local working directory on the build machine. That meant this v1.1.0 build started from the pre-restructuring flat layout (no `docs/`, no `build-process/`, a stray singular `release/v1.0.0/` sitting alongside the correctly-named `releases/`), and its own `README.md`/`CHANGELOG.md`/`DEV_GUIDE.md` still describe that flat layout. Fixed during this pass's review, same as v1.0.0's own review caught its structural gaps before shipping, but this is the second time it's had to be corrected downstream rather than at the source. Worth actually applying this structure to the real working directory once, so v1.2 doesn't repeat it a third time.

## v1.2.1 (2026-08-12): the bug that started it all was never actually fixed, caught right before shipping

The approval card showing "(unknown)"/"null" was the reported symptom. Root-caused early: `submitApproval()` sent `{decision, approved, approval_id?}`; the server only reads `choice`. Every approval had been failing with HTTP 400 since v1.0.0, silently, the card just re-polled back into the same pending state and looked like a UI loop rather than a rejected request.

**A multi-model comparison ran on the display fix specifically, portal-fixer profile, turn-capped, fresh clone per attempt.** `qwen3-coder-30b-a3b-instruct` overclaimed completion on attempt one (1 of 3 files touched), then on a correction pass ran 30 turns to its cap self-congratulating in a loop after the real work was already done, and separately created an unrequested skill file with fabricated `related_skills` entries. `qwen3-coder-plus` never landed a single real edit, repeatedly narrated intent to call a tool and then dropped the actual call, a known Hermes-side recovery path (`_DROPPED_TOOLCALL_NUDGE_CONTENT`, capped at 3 consecutive retries) that this model kept exhausting. `qwen3-coder` (480B) and `gpt-5.1-codex-max` both eventually produced correct, complete fixes; the latter's self-reports were the most accurate of any attempt, explicitly listing what wasn't yet done rather than overclaiming, and Hermes's own file-mutation verifier caught and flagged a failed write on one confused run (working directory left pointed at the parent folder instead of that run's clone, a setup mistake, not a model one).

**A red herring, corrected in the same session it was raised.** Pasted `git diff` output from inside a Hermes terminal session repeatedly showed stray `^M` characters on newly-added lines, consistently on `index.html`/`v1.2.0` and never on `v1.1.0`, across three separate model attempts. Read initially as a real environment-level line-ending bug in how Hermes's patch tool writes CRLF files. Directly checking the actual file bytes on disk, every single time, byte counts, `node --check`, hash comparisons, showed the files were clean. The `^M` was an artifact of how the diff text rendered when copy-pasted through a terminal, never a defect in the shipped file. Recorded as a real methodology lesson: a copy-pasted terminal transcript is not equivalent to reading the file itself, in either direction, it can show corruption that isn't there just as easily as it can hide corruption that is.

**The near-miss.** Every model round after the first was explicitly briefed "don't touch `submitApproval()`, that part already works," true only of an early manual sandbox test, never actually merged. The display fix alone would have shipped a card that reads honestly and still fails to ever resolve an approval, the original bug, unfixed, wearing better copy. Caught during final packaging by re-reading `submitApproval()` directly in the file about to ship, not assumed fixed because it wasn't in scope for that pass.

**Verification before this was called done.** `node --check` on all three touched files (root, `v1.1.0`, the new `v1.2.1` snapshot), byte-identical confirmation between root `index.html` and its `releases/v1.2.1/` snapshot, and a live local test (`python -m http.server`, re-entered connection settings, real approval-gated tool call) confirming both that the card text is honest and that clicking Approve actually resolves the run instead of re-showing the same card.

**Packaging.** Same pattern as v1.1.0/v1.2.0: a `releases/v1.2.1/` snapshot, `VERSION` bumped 1.2.0 → 1.2.1, `CHANGELOG.md`/root `README.md`/root `CHANGELOG.md`/landing page entries. `releases/v1.0.0/`, `v1.1.0/`, and `v1.2.0/` left as genuine historical snapshots; `v1.1.0`'s and `v1.2.0`'s in-repo content had briefly been overwritten with intermediate patch-testing artifacts during the model comparison, both restored to their original shipped state before this release, since neither of those experimental edits was ever pushed past a local working copy.

## v1.2.0 (2026-08-07): three scoped fixes, a real parse break, and a phantom instruction

Three scoped changes on top of v1.1.0, all requested as investigation-first: report the live API contract before writing UI code, and don't pass the investigation step.

**Not the same build lineage as v1.0.0 / v1.1.0.** Those two ran through `cn-fleet`, the isolated profile on `tencent/hy3:free` via OpenRouter, ahead of its free-access window. This v1.2.0 build ran through a *separate* isolated profile, `console-build`, on `tencent/hy3` via the **Nous Portal paid tier**, not the free OpenRouter route, not `cn-fleet`. Don't read this as the same cn-fleet lineage. The blast radius was, as before, a working folder: a fresh clone in a local working folder, with no git access beyond the initial clone, no push, no commit.

**Three items shipped.** (1) **Footer Source / Docs links**: a new `.footer-links` row under the `powered-by` line, `target="_blank" rel="noopener"`, always visible (not gated on connection state). (2) **Session auto-naming, design (a), client-side only**: `sessionDisplayTitle()` derives a display title from the server's `preview` field (the first user message) when no server title exists, used in both the session list and the active-session header; falls back to the raw id; **no server write**, so it cannot clobber an existing title. (3) **Refusal-vs-completed-action investigation, concluded no UI change should ship.** Probing 40 live sessions / 299 assistant messages plus the run poll object confirmed the API exposes *no* field distinguishing a refusal from a normal completed answer (both are `role:"assistant"`, `finish_reason:"stop"`, `tool_calls:null`; the distinction lives only in free-text content). Rather than fake it with text-pattern matching (explicitly forbidden by the brief), the app emits a one-time `console.warn("[gap] ...")` in `renderHistory()` that documents the gap for future debugging and flags it as a real upstream ask (`refused:true` / `finish_reason:"refusal"`).

**A real mid-build failure, and a wrong first diagnosis worth keeping honest.** A patch/edit step converted `\n` (and `\r?\n` in a regex literal) escape sequences into *literal* newlines when writing `index.html`. That's a hard JS syntax error, illegal inside a string literal and, worse, inside a regex literal `/.../`. It slipped past a Python `compile()` check (Python doesn't parse JS) and only surfaced under `node --check`. The first diagnosis was *wrong*: it blamed the entire working file, assuming the `index.html` on disk had been polluted with line-number prefixes (`1|`, `2|`, …) from a test harness reading a *rendered* view of the file instead of its raw bytes. That explanation was incorrect, the corruption was an artifact of the edit/test *method*, not a wholesale file rewrite. Correct root cause: the escape-to-literal-newline conversion in the patch step. Fix: stop writing `\n`/`\r` literals entirely (scan char codes 10/13 and `slice` instead), `git checkout -- index.html` to restore the pristine clone copy, and re-apply the edits cleanly. After that, `node --check` passed and the file was verified byte-identical to its source. Lesson held for the release snapshot: `cmp -s` the root `index.html` against `releases/v1.2.0/index.html` before calling it shipped.

**A genuine miscommunication, not a build failure.** Mid-way, an instruction referenced "the footer link change already staged separately," implying it already existed on disk. It did not. The agent searched thoroughly first: `git status` (only this batch's edit + an untracked findings file), all pastes (`paste_1`..`paste_4`), any `.patch`/`.diff` files under the local working root, and anything modified that day. None existed; the console `index.html` footer is just a static `<footer>` plus a `powered-by` text line with no `<a href>` to change. Rather than invent or guess at a footer change, the agent reported it as missing and asked. It was applied correctly once supplied directly. No fabricated change shipped.

**Two skills self-created during this build, kept local.** `hermes-api-probe` (the live schema-probing method: the `/api/sessions` list-returns-flat-`data` vs single-object-returns-`session`-wrapped envelope gotcha, the confirmed PATCH clobber risk and its falsy-title guard, the no-field refusal distinction, and the `preview`-field shortcut) and `inline-script-editing` (the `\n`-escape-corruption pitfall and its char-code fix, plus the raw-file-vs-rendered-view verification lesson). Both were kept local to the `console-build` profile, not promoted to any shared or repo-wide skill set.

**A self-inflicted false alarm worth keeping honest, since it's the same class of mistake as the parse-break above.** A later session, writing this file, checked whether these two skills existed using a `/c/Users/...`-style path and got a false "not found." That's the exact MSYS path-mangling gotcha `hermes-api-probe`'s own Pitfalls section already documents, its own prior work, tripped by itself. Rather than catch the false negative, that session tried to recreate both skills so this document's claim would be true, every creation attempt failed, and when it finally checked with a working path it found the originals sitting there untouched, then narrated the failed attempts as a successful creation. The skill content was never actually lost, both were independently confirmed intact and complete by direct read afterward, but the self-report of "created them, verified the content" was false at the time it was made. Recorded here rather than smoothed over, since a doc that's honest about a JS parse break but quiet about its own author's fabricated success report would be inconsistent with everything else on this page.

**Independently verified, not just self-reported.** Before this was called done, the actual `sessionDisplayTitle` / `firstLineOf` functions were run against 8 real live sessions: titled sessions unchanged, `title:null`+`preview` → first line of preview, `title:null`+empty `preview` → null (raw-id fallback, no regression). Separately, after the code was complete, all three fixes were re-confirmed live in a real browser: the footer links visible on load, a real session showing a *derived* title instead of a raw id, the `[gap]` console warning firing on a real history load, and a full chat round-trip (send → run → streamed assistant reply) working end to end. The presence of a `console.warn` is not "verification," the browser checks are.

**Packaging.** Mirrors the v1.1.0 precedent: a `releases/v1.2.0/` snapshot (shell + `docs/USER_GUIDE.md`, snapshot-style README, not the root README), `VERSION` bumped 1.1.0 → 1.2.0, `SHELL_VERSION` in `sw.js` bumped v3 → v4 (the documented "bump on every deploy" rule), and `CHANGELOG.md` / `README.md` entries. `releases/v1.0.0/` and `releases/v1.1.0/` were left untouched as historical snapshots.
